# 数据说明

## 数据来源

本程序读取雷达 TCP 连接上的字节流，再交给既有 `ProtocolsLib.dll` 解析。保存的字节是电脑实际收到的应用层数据；解析出来的目标是协议库的输出。

本版不生成车辆来充当设备输出。离线测试所用的输入必须明确标记为测试或回放数据，不能计入道路实采结果。

离线自测生成的会话仅放在 `test-output` 下，元信息中 `source_kind` 为 `synthetic_self_test`。验收实际道路数据时应先核对数据来源。

## TCP 接收边界不是协议帧边界

同样的一段雷达报文，可能在一次 `Read` 中收到，也可能分成多次。多段报文也可能在一次 `Read` 中一起到达。

因此 `raw-index.csv` 描述的是本机接收过程：

- 字节偏移和长度用于在 `raw.bin` 中定位数据；
- 接收序号用于追踪程序执行顺序；
- 时间用于分析接收延迟和本机记录过程。

这些信息不能直接当作设备帧号、采样周期或车辆轨迹点之间的准确物理时间差。协议库的完整报文提取也需要接受跨接收块测试。

`raw-index.csv` 字段如下：

| 字段 | 含义 |
| --- | --- |
| `recv_seq` | 本机接收事件顺序号，不是设备帧号。 |
| `offset` | 本次字节块在 `raw.bin` 中的起始偏移。 |
| `length` | 本次字节块长度，单位为字节。 |
| `host_received_utc` | 主机记录接收的 UTC 时间，ISO 8601 格式。 |
| `host_monotonic_ticks` | 主机单调计数器值；换算秒数需要会话元信息中的计数器频率。 |

接收序号和目标事件序号按当前连接累计，同一连接的第二次保存不必从 1 开始。它们不是跨程序或跨实验的全局身份。

## 主机时间

UTC 时间用于明确日期和跨文件查找。单调计时用于一个程序运行周期内计算间隔。不同电脑、不同程序启动之间的单调计数不能直接互相比较。

电脑接收时间包含设备输出、传输和系统调度等延迟。摄像头录像还包含曝光、编码、网络、解码和录制延迟。把摄像头画面上的时钟调到电脑时间，并不能消除这些延迟。

风险场研究需要两路精确对齐时，应另做同步与延迟测量，保存校准结果。

`vendor_parse_time` 已通过协议库检查确认：它在主机解析时调用 `DateTime.Now` 生成，格式为 `HH:mm:ss.fff`。它没有日期和时区信息，不能用于硬件同步，也不能单独跨午夜排序。

## 目标记录

`targets.csv` 一行代表一次协议目标事件。它不是“所有空帧也均有记录”的逐帧表，记录数不能直接除以宣称频率换算实验长度。

| 字段 | 含义 |
| --- | --- |
| `target_seq` | 本机目标事件序号，不是设备帧号。 |
| `recv_seq` | 触发这次解析输出的本机接收事件序号；报文可能跨多个接收事件。 |
| `host_received_utc`, `host_monotonic_ticks` | 关联接收事件的主机时间信息。 |
| `track_id` | 厂家目标 ID。 |
| `x_lateral`, `y_longitudinal` | 协议库提供的横向、纵向位置。 |
| `vx_lateral`, `vy_longitudinal` | 协议库提供的横向、纵向速度。 |
| `range`, `angle`, `velocity` | 协议库提供的距离、角度、速度。 |
| `class`, `dyn_prop` | 分类与运动属性字段。 |
| `rcs`, `snr`, `energy` | 协议库提供的特征字段；是否有效需实测。 |
| `vendor_parse_time` | 厂家协议库在主机上生成的解析时间字符串。 |
| `radar_type` | 解析目标附带的雷达类型信息。 |

当前适配器把尚未可靠支持的标量速度 `velocity`、`snr`、`energy` 设为缺失值，CSV 中显示为空。缺失值与物理量为零不同。横纵向速度分量保留协议库解析结果。

以下内容需要真实目标样本与厂家说明共同确认：

| 内容 | 为什么要核实 |
| --- | --- |
| 横向、纵向轴及正负方向 | 关系到车道映射和轨迹方向。 |
| 距离、角度、速度的单位 | 关系到数值计算，不能仅凭变量名确定。 |
| 分类、RCS、SNR 等字段的有效性 | 特定协议或固件可能不输出某些字段，默认零值不等于物理量为零。 |
| 目标 ID 的生命周期 | 遮挡、离开视野或设备重启后可能复用。 |
| 完整目标周期与空周期的表示 | 关系到完整帧重建和掉帧判定。 |

当前仅确认协议库提供周期开始通知，没有已经验证的完整周期结束信息。本版不据此推断硬件帧完整性、设备帧号或掉帧率。

## 保存与停止

正常停止录制应关闭并刷新本次会话文件。检查一次采集时，应同时查看会话元信息、事件记录及数据文件，而不只看目录里是否出现了文件。

`session.json` 开始时 `finalized=false`，正常完成文件刷新和关闭后为 `true`。`completion_reason` 说明结束原因，`faulted` 和 `fault_message` 记录保存器故障。文件正常关闭不等于采集过程中从未断线；例如网络异常结束时，已收到的数据仍可被正常关闭，需同时查看结束原因和事件日志。

开始保存会重置协议解析器的残留缓存。会话可能从雷达报文中间开始，解析器需要重新寻找下一条完整报文；末尾原始字节也可能只有半条报文。本版不把这些边界虚构为完整帧。

如果网络正常但前方没有目标，目标表可以只有表头。连接空闲、已收到协议数据但没有目标、网络已断开是三种不同情况。

异常断电、进程被强制结束、磁盘写入失败可能留下不完整会话。这类会话需要根据实际文件和事件记录判断，不能自动当作完整实验。

## 界面回放

界面读取 `session.json` 的计时频率，并流式读取 `targets.csv`，按照各目标的主机单调时间间隔显示。它不重新解析 `raw.bin`，也不能证明原始协议字段或设备帧边界正确。

原始字节与索引供后续复查和重新解析；离线测试可单独验证重新解析链路。两种检查应分别记录。
